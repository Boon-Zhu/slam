# DOGZILLA S2 室内建图与定位：第一版方案共识

首次讨论日期：2026-10-26。顶层架构共识更新日期：2026-10-30。

本文记录当前已确认的需求、顶层架构及待讨论事项。本轮顶层架构访谈已完成，下一步按四个模块分别讨论具体任务和实现。本文不代表已经实现或通过真机验证；候选软件仍未最终选型。

## 1. 目标与资源

第一版以工程上稳定建图、定位和可演示为目标，不以算法创新或论文贡献作为验收条件。

- 时间：两周内完成可演示版本。
- 人员：4 人，每人每周至少投入 10 小时，两周合计至少约 80 人时。
- 平台：DOGZILLA S2，基于树莓派的嵌入式计算平台。
- 技术栈：ROS2。
- 激光雷达：MS200，由用户确认。
- 硬件约束：保持原装；当前及可预见阶段不修改原装硬件，不调整传感器安装或增加传感器。
- 运动控制：使用人工遥控或已有控制代码，保留现有底层步态控制。
- 部署：验收时建图、定位全部运行在树莓派上。外部电脑用于遥控、可视化与实验分析；开发阶段允许在电脑上离线回放数据。

## 2. 演示环境与功能边界

演示场地为约 15 平方米的可控室内房间，包含需要绕行的障碍物，不要求跨越障碍物。

演示障碍物应在雷达扫描高度处可见，且能被 MS200 稳定检测。演示前逐一验证检测效果。第一版不承诺检测低矮物体、玻璃、悬空突出物或地面落差，也不承诺在任意环境下防碰撞。

第一版包含：

1. 人工遥控机器人运动并建图。
2. 保存地图。
3. 重启后加载地图并恢复定位。
4. 遥控过程中检测障碍、限制危险方向的运动并发出提示。
5. 雷达数据或遥控连接中断时停止运动。

第一版不要求自主探索、自动规划绕行路线或自主到点导航。关机前回到停靠位由人工遥控完成。

本版由操作人员明确选择两种独立运行模式：

- 建图模式：人工遥控采集环境，生成并保存地图。
- 定位模式：加载已有地图，从停靠位初始化并持续定位，不修改地图。

两种模式均启用遥控运动保护。切换时先停止运动，由 D 协调流程、B 提供对应能力。后续规划在定位模式下增加地图修正与自主导航；未来导航指令也必须经过 C 的运动保护，再交给 A 执行，本版不实现这些扩展。

## 3. 地图保存与重启定位

已确定支持保存地图与重启后定位，采用固定停靠位约束降低首次实现复杂度。

预期流程：

1. 建图完成后保存地图，设定固定停靠位及朝向；可以使用地面位置和方向标记辅助人工对齐。
2. 关机前人工遥控回到该停靠位，停稳后记录地图坐标系中的位置与朝向。
3. 保存位姿及对应地图标识，确保写盘完成，正常关闭系统后再断电。
4. 断电期间不搬动机器人。
5. 重启后加载同一地图，以保存位姿初始化定位，再用实时激光扫描校正。

指定的目标位姿不等于实际停靠位姿，不能仅凭已发送运动指令认定机器人到达目标。保存位姿作为带有误差的初始估计，不视为真实位置。

如果机器人断电期间被搬动，则上述初始化前提失效，需要人工重新指定初始位姿。第一版不要求从任意未知位置自动完成全局重定位。

树莓派平台支持通过 microSD 或外部 USB 存储保存文件，优先考虑现有系统存储介质。实际容量、可写路径和持久化配置需真机检查；地图文件格式随定位方案确定。

### 3.1 单地图与替换规则

- 第一版只维护一张当前地图，不提供多地图管理。
- 新地图完整保存成功后自动替换原地图，不增加人工确认环节。
- 开始新建图时保留原文件；若建图中断或保存失败，原地图仍可用。用于完整写入的临时文件不构成多地图管理。
- 替换成功后，原地图绑定的停靠位与启动位姿失效，必须在新地图中重新记录。
- 提供当前地图导出选项，排在第一版最后完成。B 提供保存与导出能力，D 提供操作入口和流程。

## 4. 定位与防碰撞验收

定位位置误差的初步目标为约 50 厘米。具体统计口径、参考测量方法、朝向误差、稳定运行时长和重启定位耗时尚未确定。

定位误差与防碰撞分别验收：

- 定位误差：估计的地图位置与实际位置的偏差。
- 防碰撞：在约定的障碍物、速度和环境条件下，能否及时限制运动并避免碰撞。

地图显示整齐不等于定位准确，定位达标也不代表防碰撞达标。需要采用实际参考点和重复试验验证；当前没有实测结果。

## 5. 遥控运动保护

已选择“人工遥控 + 系统运动限制”，具体绕行由人工完成。

### 5.1 障碍响应

- 检测到障碍后，限制朝向障碍的运动。
- 允许向已确认有足够空间的方向低速退开。
- 转身也需要检查机身扫过的空间，不能默认原地转身安全。
- 向遥控端发送提示；提示协议、界面和具体方式留待后续讨论。

遥控指令应先经过运动保护模块，再交给底层运动接口，避免遥控路径绕过保护。

### 5.2 数据与通信故障

- 雷达数据中断或遥控连接断开时，自动停止运动。
- 连接可用时，向遥控端提示故障。
- 数据或连接恢复后，必须收到新的遥控指令才继续运动，不自动恢复执行中断前的指令。
- 超时时间依据传感器频率和实测通信延迟确定，目前不设定具体数值。
- 定位失效但雷达与遥控正常时，允许继续受保护的人工遥控，并明确提示定位不可用。
- 禁止将无效位姿保存为下次启动位置。未来自主导航在定位失效时必须暂停。

保护距离、机身轮廓、停止距离、允许速度及故障恢复判定仍需设计和测试。

## 6. 已确认的顶层架构与候选组件

### 6.1 四个模块的职责

| 模块 | 负责范围 | 对外交付 |
| --- | --- | --- |
| A：设备接入与运动接口 | 原装传感器接入、时间戳与坐标系核实、底层运动和停止接口 | 传感器数据、设备状态、统一运动接口及首份真机录包 |
| B：运动估计、建图与定位 | 里程计方案、地图生成与保存、加载地图、恢复定位及地图导出 | 地图、位姿、定位状态、保存／恢复／导出能力 |
| C：遥控与运动保护 | 遥控输入、障碍检查、危险方向限制、数据与通信故障停车 | 受保护的运动指令、限制与故障原因 |
| D：运行流程与集成验证 | 启动与模式切换、关机保存及重启流程协调、状态汇总、回放与验收 | 集成配置、可重复演示流程、测试记录 |

B 统一负责运动估计方案；A 负责提供可用的原始数据和原有反馈，不默认厂商里程计可信。D 调用 B 的地图能力，不重复实现地图逻辑；C 执行运动限制，A 提供实际运动与停止能力。演示期间所有运动指令必须经过 C。

D 模块负责人兼任集成负责人，协调 `develop` 合入、真机联调和交付验收。各模块负责人负责自身质量和问题修复，D 不替代其他模块修复内部问题。具体人员尚未分配，模块划分也不意味着工作量完全相等。

### 6.2 依赖与并行关系

```text
共同接口约定 → A / B / C / D 并行开发

A 传感器数据、时间戳、坐标系及反馈 → B 建图定位
A 扫描数据、运动与停止接口        → C 遥控保护
遥控输入 → C 受保护指令 → A 运动执行
A 设备状态 / B 地图与定位状态 / C 保护状态 → D 运行与集成
```

上述依赖阻塞完整联调，不要求上游全部完成后下游才能开工：

- A 优先核实真机并交付最小设备接口和录包。
- B 可先搭建建图定位、地图保存与恢复流程，用录包开发；实际效果依赖 A 的真实数据及反馈。
- C 可先用模拟输入验证指令限制与故障逻辑，再用录包验证障碍检测。实时障碍保护不等待 B 完成建图，也不以全局定位正常为前提。
- D 从第一天组织启动流程、状态汇总、集成配置和验收步骤，完整演示依赖 A/B/C 的可运行版本。

共同使用 A 尽早录制的一份真机数据，包含传感器、坐标变换及可用运动反馈。B 用于建图定位验证，C 用于障碍检测验证，D 用于集成回归。录包不能证明实际停车距离、运动响应或断连停车效果，这些仍须真机联调。共享真机时间需要统一协调。

### 6.3 接口协作规则

统一接口约定是四个分支并行开发的共同基线，先确定输入输出和责任归属，再分别实现：

- A：传感器数据、坐标系、设备状态、运动与停止接口。
- B：地图、位姿、定位状态、保存／恢复／导出能力。
- C：遥控输入、受保护指令、限制及停车原因。
- D：各模块调用方式、就绪判断、启动／切换／关闭协调。

具体话题名、消息类型、调用方式和错误语义留给后续分工讨论。跨模块接口变更由相关双方负责人和 D 共同确认，模块内部实现由负责人决定。

### 6.4 候选技术组件（未最终选型）

建议以二维激光 SLAM 为基线，复用厂商设备驱动与底层控制。建立独立的 ROS2 集成项目管理设备适配、启动文件、参数、地图和评测，优先配置已有软件，必要时再修改或 fork 上游项目。

```text
MS200 雷达 → ROS2 驱动 ───────────→ 建图 / 已有地图定位
                    ├→ 局部运动估计 ──────↑
                    └→ 障碍检测 ──────────┐
可用的 IMU / 运动反馈 → 局部运动估计       │
                                         ↓
遥控指令 ───────────────────────→ 运动保护 → 原有运动接口 → 步态控制
                                         │
                                         └→ 遥控端状态提示

地图 / 初始位姿 ↔ 持久化存储
传感器 / TF / 位姿 / 状态 → 可视化、录包与评测
```

上图表示职责关系，不代表已确认真机的传感器话题或数据质量。IMU、运动反馈是否可用，以及局部运动估计采用何种输入，需要检查实际驱动与数据。

候选组件：

| 组件 | 候选用途 | 当前状态 |
| --- | --- | --- |
| Yahboom DOGZILLA 代码与示例 | 设备驱动、运动控制、厂商建图导航基线 | 待检查实际源码、设备版本和许可证 |
| slam_toolbox | 二维激光建图、闭环、地图保存；也可评估其定位模式 | 建议的建图基线，未最终选型 |
| Nav2 AMCL | 已有静态地图上的定位 | 定位候选，不意味着引入完整自主导航 |

建图与已有地图定位采用不同运行模式。ROS2 坐标关系通常为 `map → odom → base_link → 传感器坐标系`，每段变换应有唯一且明确的发布者；实际是否使用 `base_footprint` 等中间坐标系，以设备模型和设计为准。

## 7. 真机核实重点

以下均未验证，不能当作已具备的能力：

- 树莓派具体型号、内存、操作系统、ROS2 版本及容器使用情况。厂商公开资料中的 Pi 5 / Humble 不能代替实际设备检查。
- MS200 驱动、扫描频率、时间戳、坐标系、测距表现和可用视野。
- 原装安装对应的传感器外参与 TF 是否正确；保持原装不代表无需检查配置。
- IMU 和运动反馈是否可获取，频率、时间同步及数据质量如何。
- `/odom` 是否存在、如何产生，是否只是积分控制指令；指令速度不能直接等同于实际位移。
- 原有遥控和运动接口是否能统一接入运动保护，停止指令是否及时生效。
- 行走时机身俯仰、横滚与起伏是否影响二维扫描和建图。
- 树莓派运行时延迟、CPU、内存、温度及存储情况。

不修改硬件的前提下，可评估软件配置、允许速度与现有步态选择。若仍不能满足目标，应记录能力限制，不默认通过硬件升级解决。

## 8. 分支策略与集成里程碑

### 8.1 分支规则

以下为已确认的组织方案，不表示这些分支已经创建。

```text
main                         稳定交付版本
 └─ develop                  日常集成与联调
     ├─ feat/device-adapter       A
     ├─ feat/slam-localization    B
     ├─ feat/teleop-protection    C
     └─ feat/system-integration   D
```

- `develop` 初始从 `main` 创建，四个功能分支从 `develop` 创建。
- 功能分支完成可验证的小阶段后合入 `develop`，其他功能分支持续同步 `develop`。
- 实际多人联调在 `develop` 进行；D 的功能分支用于开发集成代码，不代替共同集成分支。
- `develop` 完成整体验收后合入 `main` 交付。交付后两者保持一致，开发期间允许 `develop` 领先。
- 如 `main` 有直接修复，及时同步回 `develop`。

### 8.2 三个集成里程碑

| 里程碑 | 集成验收内容 |
| --- | --- |
| 1. 受保护遥控可用 | 传感器与运动接口打通，遇障限制运动、断连停车生效，产出首份真机录包 |
| 2. 建图与定位闭环可用 | 树莓派建图、保存、固定停靠位重启定位可用，验证新地图自动替换流程 |
| 3. 演示交付可用 | 重复验证完整流程，检查约 50 厘米定位目标及故障处理，最后补齐地图导出，在 `develop` 验收后合入 `main` |

这是集成验收顺序，不是各模块顺序开发。D 协调里程碑，各模块交付对应能力；具体日期、任务量、测试细则和人员安排留到分工讨论，不在本文中推定。

## 9. 接下来分别讨论的任务

以下是待讨论清单，不是已确定的实现方案。先共同约定接口，再按四个分支展开，最终由 D 汇总依赖和排期。

### 9.1 共同讨论：接口基线与人员安排

- 为四个模块指定负责人，确认 D 的集成职责和共享真机时间。
- 确认模块接口的输入输出、状态与错误语义，划分配置和公共文件的维护责任。
- 明确每段 TF 的发布者、时间基准、数据有效性和运动指令通路。
- 将两周目标拆解到三个里程碑，确定每个分支的最小交付与联调条件。

预期产出：接口约定、负责人清单、共享设备安排和里程碑任务表。

### 9.2 A：`feat/device-adapter`

- 核实系统版本、厂商驱动、原有控制代码与可复用范围。
- 检查 MS200、IMU 和运动反馈的实际接口、时间戳、频率、TF 与数据质量。
- 查明现有 `/odom` 的来源，将证据交给 B 决定运动估计方案。
- 明确统一运动与停止接口，以及如何避免原有遥控通路绕过 C。
- 与 B/C/D 确定首份录包的内容、场景、元数据和回放方式。

预期产出：设备核实记录、接口清单、最小驱动与运动适配方案、首份录包计划。

### 9.3 B：`feat/slam-localization`

- 选择建图和定位组件，决定原有里程计是否可用、是否需要独立激光里程计或融合。
- 定义建图／定位模式的输入输出、定位有效性判定及 TF 责任。
- 设计单地图保存、完整写入后替换、启动位姿关联与失效规则。
- 设计固定停靠位初始化、定位失败与人工重新初始化流程。
- 与 D 明确约 50 厘米目标的误差统计、参考测量、朝向要求、恢复耗时和重复次数。
- 确定地图导出内容与接口，按约定在第一版最后完成。

预期产出：算法选型依据、地图与位姿接口、回放验证方案、定位验收细则及分阶段任务。

### 9.4 C：`feat/teleop-protection`

- 明确遥控输入来源和统一指令通路，设计运动限制逻辑。
- 确定机身轮廓、保护距离、速度上限以及转向、横移和退开空间的判断方法。
- 与 A 实测运动响应和停止距离，确定雷达与遥控超时及恢复条件。
- 明确定位失效时的受保护遥控行为，以及限制／故障状态输出。
- 与 D 讨论遥控端提示的传输方式、内容和展示方式。
- 划分模拟输入、录包与真机测试范围，制定防碰撞和故障停车验收用例。

预期产出：运动保护规则、状态接口、遥控提示约定、测试用例及分阶段任务。

### 9.5 D：`feat/system-integration`

- 组织统一启动、就绪检查、模式切换、地图保存、正常关机与重启流程。
- 明确如何调用 B 的地图能力，以及如何汇总 A/B/C 的状态和故障。
- 设计操作入口、状态展示、录包回放和可重复演示步骤。
- 与各负责人确定 `develop` 合入条件、集成回归内容及真机联调安排。
