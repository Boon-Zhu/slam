## 1. 目标与资源

第一版以工程上稳定建图、定位和可演示为目标，不以算法创新或论文贡献作为验收条件。

- 时间：两周内完成快速验证版，达到 §8.2 的里程碑 2；交付版日期待首次真机采集与快速验证结果出来后，由各模块估算工作量、D 汇总。具体日期暂不确定，团队讨论后由 D 汇总并写入 issue；不视为两周周期已经开始。
- 人员：4 人，每人每周至少投入 10 小时，两周合计至少约 80 人时。
- 平台：DOGZILLA S2，基于树莓派的嵌入式计算平台。
- 技术栈：Ubuntu 22.04 + ROS2 Humble，默认 Python 3.10，按需 C++17；Python 检查采用 Ruff、mypy、pytest，工具版本与 CI 配置待试运行。机器人保留 Debian 宿主及厂商 Humble 容器，D 管理机器人环境。
- 激光雷达：MS200，由用户确认。
- 硬件约束：保持原装；当前及可预见阶段不修改原装硬件，不调整传感器安装或增加传感器。
- 运动控制：使用人工遥控或已有控制代码，保留现有底层步态控制。
- 部署：验收时建图、定位全部运行在树莓派上。外部电脑用于遥控、可视化与实验分析；开发阶段允许在电脑上离线回放数据。

## 2. 演示环境与功能边界

演示场地为约 15 平方米的可控室内房间，包含需要绕行的障碍物，不要求跨越障碍物。

演示障碍物应在雷达扫描高度处可见，且能被 MS200 稳定检测。演示前逐一验证检测效果。第一版不承诺检测低矮物体、玻璃、悬空突出物或地面落差，也不承诺在任意环境下防碰撞。

| 功能 | 快速验证版 | 交付版 |
| --- | --- | --- |
| 持续人工遥控、采集、建图与地图保存 | 跑通闭环，维护单张当前地图 | 完整验证并引入多地图保存 |
| 障碍提示与危险方向限制 | 验证实际实现的典型行为 | 完整验证约定范围 |
| 已有地图定位、固定停靠位重启与模式切换 | 延期，保留建图必需的运动估计 | 实现与验收 |
| 故障处理 | 采用 §5 的快速验证规则，明确未验证与延期项 | 完整验证约定故障；雷达降级模式是否保留另定 |

两个版本均不要求自主探索、自动规划绕行或自主到点导航。场景限静态障碍；关机前返回停靠位由人工遥控完成。

交付版由操作人员选择互斥的建图与定位模式：建图模式生成地图；定位模式加载已有地图、不修改地图。模式切换先经 C/A 停止，由 D 请求 B 切换并反馈结果，失败不得显示成功，成功也不自动恢复运动。未来导航扩展同样必须经过 C，目前不在交付范围内。

## 3. 地图保存与重启定位

快速验证版只要求地图保存；以下固定停靠位与重启定位流程适用于交付版。

预期流程：

1. 建图完成后保存地图，设定固定停靠位及朝向；可以使用地面位置和方向标记辅助人工对齐。
2. 关机前人工遥控回到该停靠位，停稳后记录地图坐标系中的位置与朝向。
3. 保存位姿及对应地图标识，确保写盘完成，正常关闭系统后再断电。
4. 断电期间不搬动机器人。
5. 重启后加载同一地图，以保存位姿初始化定位，再用实时激光扫描校正。

指定的目标位姿不等于实际停靠位姿，不能仅凭已发送运动指令认定机器人到达目标。保存位姿作为带有误差的初始估计，不视为真实位置。

如果机器人断电期间被搬动，则上述初始化前提失效，需要人工重新指定初始位姿。第一版不要求从任意未知位置自动完成全局重定位。

树莓派平台支持通过 microSD 或外部 USB 存储保存文件，优先考虑现有系统存储介质。实际容量、可写路径和持久化配置需真机检查；地图文件格式随定位方案确定。

### 3.1 地图保存与版本边界

- 快速验证版只维护一张当前地图。交付版引入多地图保存，命名、选择、替换与清理规则待 B/D 细化。
- 快速验证版新地图完整保存成功后自动替换原地图，不增加人工确认环节。B 提供处理中、成功或失败及原因，D 根据结果反馈。
- 开始新建图时保留原文件；若建图中断或保存失败，原地图仍可用。用于完整写入的临时文件不构成多地图管理。
- 交付版的停靠位与启动位姿必须绑定对应地图；替换地图使旧绑定失效，需重新记录。快速验证版保存不依赖停靠位绑定。
- 地图导出归入交付版。B 提供保存与导出能力，D 提供操作入口和流程。

## 4. 定位与防碰撞验收

交付版定位位置误差的初步目标为约 50 厘米；不作为快速验证版门槛。具体统计口径、参考测量方法、朝向误差、稳定运行时长和重启定位耗时尚未确定。

定位误差与防碰撞分别验收：

- 定位误差：估计的地图位置与实际位置的偏差。
- 防碰撞：在约定的障碍物、速度和环境条件下，能否及时限制运动并避免碰撞。

地图显示整齐不等于定位准确，定位达标也不代表防碰撞达标。需要采用实际参考点和重复试验验证；当前没有实测结果。

## 5. 遥控运动保护

已选择“人工遥控 + 系统运动限制”，具体绕行由人工完成。

### 5.1 障碍响应

- 所有运动均要求持续操作，松开即停止；默认无有效指令不运动。
- 检测到障碍后，限制相应方向移动；持续按键时保持原地踏步，松开则停止踏步。有效感知再次确认可通行时，保持按键可恢复移动。原地踏步的实际接口和范围仍需核实。
- 允许向已确认有足够空间的方向低速退开。
- 转身也需要检查机身扫过的空间，不能默认原地转身安全。
- 向遥控端发送提示；提示协议、界面和具体方式留待后续讨论。

用户指令统一由 D 接收，运动通路为“用户 → D → C → A”。D 不能将失效的用户操作持续续期。

### 5.2 数据与通信故障

| 层级 | 情况 | 目标响应 |
| --- | --- | --- |
| 0 | 系统正常 | 按持续操作与障碍限制规则运行 |
| 1 | 不直接影响运动执行的传感故障 | 停止平移与转向，持续操作下原地踏步，进入用户确认流程 |
| 2 | 通信故障 | 停止行为，包括停止踏步；恢复后松开再重新操作 |
| 3 | 运动模块故障或 A 自身失效 | 强制断电；实际接口及失效时可用性待核实，快速验证版不增设额外冗余 |

快速验证版由 A 检测并报告设备与数据错误，B/C 根据报告响应，D 汇总状态；不要求 B/C 各自实现完整独立数据校验。具体传感故障归级需按接口确认。

快速验证版雷达故障的特定规则：A 报告故障后停止平移和转向，在原有持续操作下保持踏步，松开则停止；D 提供确认入口，C 管理放行。确认前不接受新的运动操作，确认本身不产生运动；确认后可重新按住方向键运动，并持续提示“雷达不可用，避障未生效”，由操作者观察环境。确认不解除通信或运动故障限制。交付版是否保留该降级模式待定。

通信检测按接收端分工：D 检测操作端失联并通知 C；C 检测 D 的有效操作指令超时，经 A 停止；A 检测 C 的运动指令超时，自行停止。超时数值由实测确定，采用单调计时。A 自身失效时不能假设仍能执行断电，实际能力交 A/D 核实；仅 A→D 错误上报通道故障且其余必要链路正常时，快速验证版维持正常运行，不因此触发运动降级或停车；这不表示通道健康，也不扩大到其他链路失联。A/B/C/D 各自保留模块日志，试运行后交叉核对，D 协调核对；日志不替代运行中的故障响应。

交付版定位失效而雷达和遥控正常时，允许受保护的人工遥控并提示定位不可用；无效位姿不得保存为启动位置。保护距离、机身轮廓、停止距离与速度均需真机验证。加速度异常停机仍是可延期候选增强项。

## 6. 已确认的顶层架构与候选组件

### 6.1 四个模块的职责

| 模块 | 负责范围 | 对外交付 |
| --- | --- | --- |
| A：设备接入与运动接口 | 原装传感器接入、时间戳与坐标系核实、底层运动和停止接口 | 传感器数据、设备状态、统一运动接口及首份真机录包 |
| B：运动估计、建图与定位 | 里程计方案、地图生成与保存、加载地图、恢复定位及地图导出 | 地图、位姿、定位状态、保存／恢复／导出能力 |
| C：遥控与运动保护 | 接收 D 的操作意图、障碍检查、运动限制与故障响应 | 受保护的运动指令、限制与故障原因 |
| D：运行流程与集成验证 | 用户交互、机器人环境、启动与模式切换、保存与重启协调、状态汇总、回放与验收 | 集成配置、可重复演示流程、测试记录 |

B 统一负责运动估计方案；A 负责提供可用的原始数据和原有反馈，不默认厂商里程计可信。D 调用 B 的地图能力，不重复实现地图逻辑；C 执行运动限制，A 提供实际运动与停止能力。演示期间所有运动指令必须经过 C。

D 模块负责人兼任集成负责人，协调 `develop` 合入、真机联调和交付验收。各模块负责人负责自身质量和问题修复，D 不替代其他模块修复内部问题。主要负责人如下，成员可以跨模块协作，工位现场协调真机使用，冲突由 D 协调。

### 6.2 依赖与并行关系

```text
共同接口约定 → A / B / C / D 并行开发

A 传感器数据、时间戳、坐标系及反馈 → B 建图定位
A 扫描数据、运动与停止接口        → C 遥控保护
用户操作 → D → C 受保护指令 → A 运动执行
A 设备状态 / B 地图与定位状态 / C 保护状态 → D 运行与集成
```

上述依赖阻塞完整联调，不要求上游全部完成后下游才能开工：

- A 优先核实真机并交付最小设备接口和录包。
- B 可先搭建建图定位、地图保存与恢复流程，用录包开发；实际效果依赖 A 的真实数据及反馈。
- C 可先用模拟输入验证指令限制与故障逻辑，再用录包验证障碍检测。实时障碍保护不等待 B 完成建图，也不以全局定位正常为前提。
- D 从第一天组织启动流程、状态汇总、集成配置和验收步骤，完整演示依赖 A/B/C 的可运行版本。

首次由 A 采集所有实际可获取的数据，B/C 按需取用并反馈具体需求，不预先按猜测裁剪。B 用于建图定位验证，C 用于障碍检测验证，D 用于集成回归。录包不能证明实际停车距离、运动响应或断连停车效果，这些仍须真机联调。共享真机时间需要统一协调。

### 6.3 接口协作规则

统一接口约定是四个分支并行开发的共同基线，先确定输入输出和责任归属，再分别实现：

- A：传感器数据、坐标系、设备状态、运动与停止接口。
- B：地图、位姿、定位状态、保存／恢复／导出能力。
- C：遥控输入、受保护指令、限制及停车原因。
- D：各模块调用方式、就绪判断、启动／切换／关闭协调。

接口由提供方逐项提出、使用方确认、D 汇总单位、坐标系、时间与错误语义。A 数据接口依据实际采集形成，B/C 业务接口不必全部等待 A。A 负责机身到传感器 TF，B 负责 odom 到机身及 map 到 odom，D 协调唯一发布。模块维护自身参数，D 加载组合；数据处理使用 ROS 时间，离线回放统一跟随播放时间。跨模块接口变更由相关双方负责人和 D 共同确认，模块内部实现由负责人决定。

### 6.4 候选技术组件（未最终选型）

建议以二维激光 SLAM 为基线，复用厂商设备驱动与底层控制。建立独立的 ROS2 集成项目管理设备适配、启动文件、参数、地图和评测。已确认只采用自研代码与未修改的上游代码：优先配置已有软件或通过公开接口组合，确有缺口时自研替换最小独立节点或组件，上游库保持原样；涉及驱动协议或算法核心时先重新评估，不自动扩大重写范围。策略与工作量边界见[阶段决议 §7.19](docs/architecture/interface-baseline-decisions.md#719-已确认不维护上游修改按最小组件自研替换)。

```text
MS200 雷达 → ROS2 驱动 ───────────→ 建图 / 已有地图定位
                    ├→ 局部运动估计 ──────↑
                    └→ 障碍检测 ──────────┐
可用的 IMU / 运动反馈 → 局部运动估计       │
                                         ↓
用户操作 → D ───────────────────→ 运动保护 → 原有运动接口 → 步态控制
                                         │
                                         └→ 遥控端状态提示

地图 / 初始位姿 ↔ 持久化存储
传感器 / TF / 位姿 / 状态 → 可视化、录包与评测
```

上图表示职责关系，不代表已确认真机的传感器话题或数据质量。IMU、运动反馈是否可用，以及局部运动估计采用何种输入，需要检查实际驱动与数据。

候选组件：

| 组件 | 候选用途 | 当前状态 |
| --- | --- | --- |
| Yahboom DOGZILLA 代码与示例 | 设备驱动、运动控制、厂商示例 | 已完成部分静态源码与镜像审计，实际运行及许可证适用性仍需核实 |
| Cartographer | 厂商教程采用的建图方案 | 已查附件与镜像未发现完整可用算法链路，仍为候选 |
| slam_toolbox | 二维激光建图、闭环、地图保存；也可评估其定位模式 | 建议的建图基线，未最终选型 |
| Nav2 AMCL | 已有静态地图上的定位 | 定位候选，不意味着引入完整自主导航 |

建图与已有地图定位采用不同运行模式。ROS2 坐标关系通常为 `map → odom → base_link → 传感器坐标系`，每段变换应有唯一且明确的发布者；实际是否使用 `base_footprint` 等中间坐标系，以设备模型和设计为准。

## 7. 真机核实重点

已提供[Pi 5 镜像核查记录](docs/report/pi5-image-version-audit-2026-11-02.md)：Pi 5，Debian 12 宿主，厂商容器 Ubuntu 22.04.4 / Humble / Python 3.10.12；DOGZILLALib 3.1.9 存在所需方法，但不代表返回值或动作已验证。核查范围内未发现完整建图定位组件。

以下能力仍需核实：
- MS200 驱动、扫描频率、时间戳、坐标系、测距表现和可用视野。
- 原装安装对应的传感器外参与 TF 是否正确；保持原装不代表无需检查配置。
- IMU 和运动反馈是否可获取，频率、时间同步及数据质量如何。
- `/odom` 是否存在、如何产生，是否只是积分控制指令；指令速度不能直接等同于实际位移。
- 原有遥控和运动接口是否能统一接入运动保护，停止指令是否及时生效。
- 行走时机身俯仰、横滚与起伏是否影响二维扫描和建图。
- 树莓派运行时延迟、CPU、内存、温度及存储情况。

不修改硬件的前提下，可评估软件配置、允许速度与现有步态选择。若仍不能满足目标，应记录能力限制，不默认通过硬件升级解决。

## 8. 分支策略与集成里程碑

### 8.1 分支规则

分支与 PR 规则已调整为两条长期分支配合短期任务分支，详细约定见 [Git 提交与协作规范](docs/agents/git-workflow.md)。以下表示组织方案，不代表分支、CI 或远端保护规则已配置。

```text
main                              稳定交付版本
 └─ develop                       日常集成与联调
     ├─ feature/device-<task>      A 的具体任务
     ├─ feature/slam-<task>        B 的具体任务
     ├─ feature/protection-<task>  C 的具体任务
     └─ feature/integration-<task> D 的具体任务
```

A/B/C/D 保持模块职责，分支按任务创建、合入后删除，不维护固定模块分支。多人联调在 `develop` 进行；整体验收后通过 PR 合入 `main`。合入条件、修复分支与合并方式以协作规范为准。

### 8.2 三个集成里程碑

里程碑 1、2 属于快速验证版，里程碑 2 完成即达到该版本的完成条件；里程碑 3 属于交付版。前两项不以独立定位、定位精度、长时间稳定性或完整故障边界测试为完成门槛。

| 里程碑 | 模块最小交付与集成内容 | 完成依据 |
| --- | --- | --- |
| 1. 操作链路与首次采集打通 | D 接收用户操作并反馈状态；C 处理运动指令；A 执行、报告设备状态并采集所有实际可获取的数据；B/C 开始读取数据并反馈需求 | 真机走通“用户 → D → C → A”，产出首份录包，记录采集范围、已知缺失和问题；无需等待建图效果或独立定位完成 |
| 2. 快速验证闭环跑通 | 在里程碑 1 基础上，B 打通建图必需的运动估计、树莓派建图及单地图保存；D 协调流程并反馈保存结果；B/C 按需使用数据 | 实际走通一次“D 接收操作 → C 处理运动指令 → A 执行并采集 → B 建图并保存 → D 反馈结果”，产出一份可供 B/C 使用的录包、一张成功保存的地图及已知问题记录 |
| 3. 定位与完整流程交付 | 补齐已有地图初始化、持续定位、固定停靠位重启定位、模式切换、多地图保存与绑定管理；按实际需求优化存储并补齐地图导出 | 在树莓派重复验证约定完整流程，按确定后的统计口径检查约 50 厘米定位目标、运行稳定性、地图持久化与故障响应；形成可重复演示步骤及验收记录，在 `develop` 验收后通过 PR 合入 `main` |

快速验证版按[阶段决议](docs/architecture/interface-baseline-decisions.md)落实持续操作、运动保护及故障响应，验证实际已实现的典型行为；复杂项可按已确认原则明确延期。跑通一次闭环不代表全部保护或边界条件已验证。首份数据优先全量保留，不以存储优化为门槛。

进入交付版实现与验收前，需确定多地图管理规则、具体定位验收指标、故障检测与执行能力，以及是否保留雷达确认后降级模式。交付版完整验证针对明确约定的场景与行为；加速度异常停机仍是候选增强项，自主导航、路径规划和自主探索仍不在范围内。

这是集成验收顺序，不是各模块顺序开发。D 协调里程碑，各模块可并行准备后续能力。已确认两周目标对应快速验证版，即完成里程碑 1、2；具体日期由团队讨论后，D 汇总并写入 issue，当前未开始计时。交付版（里程碑 3）日期待首次真机采集与快速验证结果出来后，由各模块估算工作量、D 汇总，不要求两个版本均在两周内交付。

## 9. 共同基线与后续研究

### 9.1 共同讨论：接口基线与人员安排

本轮已形成“模块可以据此独立细化方案的共同基线”，详见[阶段决议](docs/architecture/interface-baseline-decisions.md)。人员、版本取舍、职责、TF、时间、配置、依赖流程、故障响应和 CI 共同要求均已记录；具体日期暂不确定，由团队讨论后交 D 汇总写入 issue。

四位成员 ID 已齐全；[本轮 Wayfinder map](https://github.com/Boon-Zhu/slam/issues/2) 已归档完成，模块研究与协调事项已发布并移交，链接见[阶段决议 §9](docs/architecture/interface-baseline-decisions.md#9-发布与记录状态)。具体接口逐项确认。模块内部实现不再纳入本轮讨论，研究发现与共同基线冲突时再交相关负责人及 D 确认。agent 开发流程仍在计划中，不视为已实现能力。

### 9.2 A：设备接入与运动接口

- 核实驱动与实际数据的单位、频率、时间戳、TF、运动反馈及已有里程计来源。
- 明确运动、停止、踏步与指令超时执行接口，核实 A 自身失效时原装系统的断电能力，与 D 确认触发路径。
- 首次采集所有实际可采集数据，提供覆盖清单、缺失项与录包，供 B/C 按需反馈。

### 9.3 B：运动估计、建图与定位

- 快速验证版选择可复用的运动估计与建图组件，落实树莓派建图和单地图保存，向 D 提供明确保存结果。
- 交付版细化定位、固定停靠位重启、多地图绑定、存储优化与导出，以及约 50 厘米目标的验收口径。

### 9.4 C：遥控与运动保护

- 在既定“用户 → D → C → A”链路中细化持续操作、障碍限制、故障确认及恢复逻辑。
- 与 A 核实踏步范围、运动响应和停止距离，确定机身范围、保护距离、速度与超时参数。
- 与 D 确认操作与状态接口；保持快速验证版和交付版的故障范围区分。

### 9.5 D：运行流程与集成验证

- 管理机器人环境，维护整机启动配置、用户入口与反馈、状态汇总及回放配置。
- 研究开发/CI 环境、依赖固定方式、工具版本与统一检查入口，完成 GitHub Actions 最小试运行。
- 汇总模块接口和已知能力缺口，协调里程碑验证；团队讨论日期后写入 issue。
- 开发者新增依赖先自行检查冲突，无冲突通过 PR 引入，有冲突提交 issue 团队讨论；机器人环境变更由 D 管理。

以上为研究与细化任务，不代表实现、CI 或真机测试已经完成。
