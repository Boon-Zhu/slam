# DOGZILLA S2 室内建图与定位：第一版方案共识

讨论记录日期：2026-10-26。

本文记录当前已确认的需求、技术方向及待讨论事项。架构访谈暂告一段落，尚未完成全部设计，也未进行真机验证。候选软件不代表已经选型或部署。

## 1. 目标与资源

第一版以工程上稳定建图、定位和可演示为目标，不以算法创新或论文贡献作为验收条件。

- 时间：两周内完成可演示版本。
- 人员：4 人，每人每周至少投入 10 小时，两周合计至少约 80 人时。
- 平台：DOGZILLA S2，基于树莓派的嵌入式计算平台。
- 技术栈：ROS2。
- 激光雷达：MS200，由用户确认。
- 硬件约束：保持原装；当前及可预见阶段不修改原装硬件，不调整传感器安装或增加传感器。
- 运动控制：使用人工遥控或已有控制代码，保留现有底层步态控制。
- 部署：验收时建图、定位全部运行在树莓派上。外部电脑用于遥控、可视化与实验分析；开发阶段允许在电脑上离线回放数据。

## 2. 演示环境与功能边界

演示场地为约 15 平方米的可控室内房间，包含需要绕行的障碍物，不要求跨越障碍物。

演示障碍物应在雷达扫描高度处可见，且能被 MS200 稳定检测。演示前逐一验证检测效果。第一版不承诺检测低矮物体、玻璃、悬空突出物或地面落差，也不承诺在任意环境下防碰撞。

第一版包含：

1. 人工遥控机器人运动并建图。
2. 保存地图。
3. 重启后加载地图并恢复定位。
4. 遥控过程中检测障碍、限制危险方向的运动并发出提示。
5. 雷达数据或遥控连接中断时停止运动。

第一版不要求自主探索、自动规划绕行路线或自主到点导航。关机前回到停靠位由人工遥控完成。

## 3. 地图保存与重启定位

已确定支持保存地图与重启后定位，采用固定停靠位约束降低首次实现复杂度。

预期流程：

1. 建图完成后保存地图，设定固定停靠位及朝向；可以使用地面位置和方向标记辅助人工对齐。
2. 关机前人工遥控回到该停靠位，停稳后记录地图坐标系中的位置与朝向。
3. 保存位姿及对应地图标识，确保写盘完成，正常关闭系统后再断电。
4. 断电期间不搬动机器人。
5. 重启后加载同一地图，以保存位姿初始化定位，再用实时激光扫描校正。

指定的目标位姿不等于实际停靠位姿，不能仅凭已发送运动指令认定机器人到达目标。保存位姿作为带有误差的初始估计，不视为真实位置。

如果机器人断电期间被搬动，则上述初始化前提失效，需要人工重新指定初始位姿。第一版不要求从任意未知位置自动完成全局重定位。

树莓派平台支持通过 microSD 或外部 USB 存储保存文件，优先考虑现有系统存储介质。实际容量、可写路径和持久化配置需真机检查；地图文件格式随定位方案确定。

## 4. 定位与防碰撞验收

定位位置误差的初步目标为约 50 厘米。具体统计口径、参考测量方法、朝向误差、稳定运行时长和重启定位耗时尚未确定。

定位误差与防碰撞分别验收：

- 定位误差：估计的地图位置与实际位置的偏差。
- 防碰撞：在约定的障碍物、速度和环境条件下，能否及时限制运动并避免碰撞。

地图显示整齐不等于定位准确，定位达标也不代表防碰撞达标。需要采用实际参考点和重复试验验证；当前没有实测结果。

## 5. 遥控运动保护

已选择“人工遥控 + 系统运动限制”，具体绕行由人工完成。

### 5.1 障碍响应

- 检测到障碍后，限制朝向障碍的运动。
- 允许向已确认有足够空间的方向低速退开。
- 转身也需要检查机身扫过的空间，不能默认原地转身安全。
- 向遥控端发送提示；提示协议、界面和具体方式留待后续讨论。

遥控指令应先经过运动保护模块，再交给底层运动接口，避免遥控路径绕过保护。

### 5.2 数据与通信故障

- 雷达数据中断或遥控连接断开时，自动停止运动。
- 连接可用时，向遥控端提示故障。
- 数据或连接恢复后，必须收到新的遥控指令才继续运动，不自动恢复执行中断前的指令。
- 超时时间依据传感器频率和实测通信延迟确定，目前不设定具体数值。

保护距离、机身轮廓、停止距离、允许速度及故障恢复判定仍需设计和测试。

## 6. 初步技术架构（候选，未最终选型）

建议以二维激光 SLAM 为基线，复用厂商设备驱动与底层控制。建立独立的 ROS2 集成项目管理设备适配、启动文件、参数、地图和评测，优先配置已有软件，必要时再修改或 fork 上游项目。

```text
MS200 雷达 → ROS2 驱动 ───────────→ 建图 / 已有地图定位
                    ├→ 局部运动估计 ──────↑
                    └→ 障碍检测 ──────────┐
可用的 IMU / 运动反馈 → 局部运动估计       │
                                         ↓
遥控指令 ───────────────────────→ 运动保护 → 原有运动接口 → 步态控制
                                         │
                                         └→ 遥控端状态提示

地图 / 初始位姿 ↔ 持久化存储
传感器 / TF / 位姿 / 状态 → 可视化、录包与评测
```

上图表示职责关系，不代表已确认真机的传感器话题或数据质量。IMU、运动反馈是否可用，以及局部运动估计采用何种输入，需要检查实际驱动与数据。

候选组件：

| 组件 | 候选用途 | 当前状态 |
| --- | --- | --- |
| Yahboom DOGZILLA 代码与示例 | 设备驱动、运动控制、厂商建图导航基线 | 待检查实际源码、设备版本和许可证 |
| slam_toolbox | 二维激光建图、闭环、地图保存；也可评估其定位模式 | 建议的建图基线，未最终选型 |
| Nav2 AMCL | 已有静态地图上的定位 | 定位候选，不意味着引入完整自主导航 |

建议将建图与已有地图定位分为不同运行模式。ROS2 坐标关系通常为 `map → odom → base_link → 传感器坐标系`，每段变换应有唯一且明确的发布者；实际是否使用 `base_footprint` 等中间坐标系，以设备模型和设计为准。

## 7. 真机核实重点

以下均未验证，不能当作已具备的能力：

- 树莓派具体型号、内存、操作系统、ROS2 版本及容器使用情况。厂商公开资料中的 Pi 5 / Humble 不能代替实际设备检查。
- MS200 驱动、扫描频率、时间戳、坐标系、测距表现和可用视野。
- 原装安装对应的传感器外参与 TF 是否正确；保持原装不代表无需检查配置。
- IMU 和运动反馈是否可获取，频率、时间同步及数据质量如何。
- `/odom` 是否存在、如何产生，是否只是积分控制指令；指令速度不能直接等同于实际位移。
- 原有遥控和运动接口是否能统一接入运动保护，停止指令是否及时生效。
- 行走时机身俯仰、横滚与起伏是否影响二维扫描和建图。
- 树莓派运行时延迟、CPU、内存、温度及存储情况。

不修改硬件的前提下，可评估软件配置、允许速度与现有步态选择。若仍不能满足目标，应记录能力限制，不默认通过硬件升级解决。
