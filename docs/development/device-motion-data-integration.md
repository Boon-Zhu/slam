# D 模块如何使用阶段数据

编写于 2026-11-18。用于组织离线回放、状态汇总、跨模块回归和真机验收。先按[数据包与离线复现](device-motion-data-package.md)核验轮次与归档。

## 两条运行路径

| 运行路径 | D 的控制面 | 启动的组件与数据 |
| --- | --- | --- |
| 离线开发与集成回归 | 选择固定轮次、ROS domain、时钟、播放速率、模块和模拟输入 | 播放器发布历史数据，B/C/D 读取，C 的指令输出接模拟执行端。TF 按此次运行的发布者表配置 |
| 真机快速验证闭环 | D 接收人为操作及保存请求，组织 A/B/C 启动和收尾，显示故障、进度与结果 | 运动沿用户→D→C→A，A 提供扫描、状态及设备错误，B 建图并保存，C 输出保护及限制原因，D 汇总 |

阶段采集现场用的是 A 的临时动作入口，已留下真机软件事件和现场观察。整机里程碑的完成证据来自 D/C/A 和 B 按正式职责运行的现场记录。地图保存由 D 调用 B 并转述结果，B 的建图与保存细节见[模块 B](device-motion-data-mapping.md)，持续操作和雷达降级见[模块 C](device-motion-data-protection.md)。

## 回放配置

1. **隔离**。按接收流程核对同版本接口与 bag。使用独立 ROS 环境、`ROS_LOCALHOST_ONLY=1` 和未占用的 `ROS_DOMAIN_ID`，只启动离线消费者及测试替身。确认环境中无物理执行端，也无通向设备控制的桥接。
2. **选播放方式**。包级核对运行 `capture_source.archive replay`，它用随机话题前缀和逐条内容检查。模块联调让消费者使用原话题或明确的重映射，并使用 `ros2 bag play` 的 `--clock`。先在静止轮次检查扫描、TF、时钟和订阅，再切动态轮次复用配置。
3. **统一时间和 TF 所有者**。处理回放数据的节点设 `use_sim_time=true`，输入时钟由同一播放器提供。记录暂停和变速行为。实机通信看门狗用单调时间，按单独的测试驱动验证；回放暂停及倍速属于离线测试条件。每条 TF 边只选一个发布者，本轮的 `base_link → laser_frame` 可由 bag 发布。
4. **核对实际接收**。先启动消费者再播放，观测 `/clock` 有更新、扫描实际到达、按扫描时间能查到 TF。包内只有一条 `/tf_static`，且 bag metadata 的 offered QoS 字段为空。给该话题显式设置 transient-local，并验证播放进程运行期间晚加入的 TF 监听者可读。如果改用独立静态 TF 发布者，则从播放配置排除 bag 同一条边。

用于模块联调的最小播放示例。将以下配置保存为工作目录里的 `replay-static-tf.yaml`。归档器生成的 `verification/replay_qos.yaml` 服务于逐条核对，会设置 volatile，模块联调采用下面的静态 TF 配置。

```yaml
/tf_static:
  reliability: reliable
  durability: transient_local
  history: keep_last
  depth: 1
```

已加载 Humble 及包内接口 overlay 并完成上述隔离设置后，在解压根目录运行。将 `dataset` 改为静止轮次可先跑接线测试。若消费者用 transient-local 订阅设备 `status` 或 `metadata`，给对应话题配置兼容的播放 QoS。

```bash
dataset="$PWD/datasets/20261111T162132-97e6f5fe7058"
ros2 bag play "$dataset/bag" --clock --delay 2 \
  --qos-profile-overrides-path "$PWD/replay-static-tf.yaml"
```

回放准备完成时，保存轮次 ID 和 manifest、模块版本、时钟和 QoS、重映射、TF 发布者表和消费者实际接收证据。比较功能结果先使用同一速率和起点，之后把变速、暂停或跳转作为单独用例。时间约定见[阶段决议 §7.25](../architecture/interface-baseline-decisions.md#725-已确认真机运行与录包回放的时间语义)。

## 汇总状态与故障

| 状态或结果 | 读哪份证据 | 在集成记录如何判读 |
| --- | --- | --- |
| 设备有端点、开始收录 | probe、`round.json`、`recorder_health.json` | 分别记录已发现、已匹配、收到及成功交给 writer 的消息。零扫描诊断可验证“能发现仍可能没有数据”的提示 |
| 设备状态与来源质量 | A 的状态/反馈与错误，`verification/quality_analysis.json` 用于历史对照 | READY 是入口状态。分别呈现雷达可用性、反馈方法的有效性、来源缺失及运动授权 |
| 保护或降级 | C 的判定和原因、D 转交的用户确认、A 的执行反馈 | D 提示原因并记录确认，C 判定是否生效并放行新的有效操作 |
| 保存地图 | B 的请求及结果 | 显示处理中、成功或失败原因。保存产物用于验证 B 所报结果，旧地图可用性按 B/D 契约检查 |
| 通常收尾与已知异常 | `round.json`、`bag_check.json`、`resources_after.json`、雷达子进程日志和 `shutdown_audit` | 分列 recorder、驱动、入口和资源释放。阶段动态 `finished` 与父进程返回 0 同时出现雷达子进程 -6，退出验收仍待完成 |
| 文件完整与回放 | `manifest.json`、导出回执及独立回放报告 | 分列哈希、文件可读、逐话题播放及模块功能结果。历史回放的通过证据独立于导出回执内的初始字段 |

跨模块日志可用轮次 ID、入口 session、可贯穿的请求标识和报告来源对齐，记录软件时间字段及现场观察依据。共享请求标识、错误类型、时序和承担者由接口双方与 D 确认。包内尾部 `shutdown_audit` 有未确认入 bag 的记录，与 bag 事件分别核对。A→D 上报单独失联的快速验证例外及各模块日志责任见[阶段决议 §7.29](../architecture/interface-baseline-decisions.md#729-已确认ad-单独上报失联与模块日志)。

## 组织下一步验收

1. **离线回归**覆盖静止、最终动态和按需模拟的故障。保存 B 的 TF/建图/保存输出、C 的输入与保护输出、D 的提示与流程结果。用两个诊断轮次复核零扫描、锁冲突和退出证据，录制期间以 recorder 健康与 ROS 订阅跟踪情况。以固定输入和可重跑的结果作为此步完成条件。
2. **快速验证真机闭环**按共同里程碑组织操作经 D/C/A、A 产出录包、B 在 Pi 上建图并保存、D 回报结果。一次可复查的现场流程、可读录包和成功保存的地图是闭环完成证据，另外记录实际停车/保护观察与已知问题。里程碑条件见[顶层方案 §8.2](../../README.md#82-三个集成里程碑)。
3. **补采与交付验收**由 A/B/C 给出所需来源、消息字段、场景、参考测量、频率或时序、验证方法和影响；D 汇总并安排实际验收。优先明确涉及动态 IMU/关节、安装外参或速度和转角参照、已知障碍/停车、相机/外部视频以及退出异常的阻塞项。独立定位、固定停靠位重启和完整保护由对应阶段完成。

验收表对每条结论同时保留**输入/场景、实际执行路径、验证等级、结果和证据路径**。验证等级写明文件检查、ROS 回放、离线模块功能或真机行为。D 汇总代表性成果及仍缺的证据，并追踪到[对应研究事项](../architecture/interface-baseline-decisions.md#9-发布与记录状态)。
