# A 设备模块：未修改上游与自研替代的成本评估

日期：2026-11-02。使用 `mattpocock-skills:research` 调研流程。本文是策略评估，不批准实现或新增接口规则；未编译、未运行厂商代码、未连接真机。

## 结论与范围

“只用未修改上游 + 自研代码”在 A 有可行的窄边界：保留可用的 MS200 驱动、串口库和底层固件，自己写启动配置、设备状态监测和一个统一串口所有者的 ROS 适配节点。优先替代有缺陷的 `base.py`、IMU/关节发布节点，而不是重写整个厂商 workspace 或雷达协议。用户已明确以最小独立节点或组件为替代边界、上游库保持原样；可行性仍依赖取得实机匹配的库及其有效性语义。

两周目标是快速验证版：设备执行和全量可获取数据采集、首份录包、树莓派建图与单地图保存闭环。独立定位、多地图、完整边界验证延期；A 的有效指令超时停车、可检测设备错误报告仍保留。雷达故障按最新确认流程停止平移/转向、持续操作时踏步，确认后可重新操作；A 提供执行能力，C 决定限制与放行，D 接收确认。不能沿用旧调查中“所有雷达故障一律停车”的描述覆盖新决议。[项目一手决议 §7.2、§7.7–§7.10、§7.14–§7.16](../architecture/interface-baseline-decisions.md)、[README §8.2](../../README.md)

## 证据可复核性

本轮已读取仓库最新决议、README 与[此前设备调查](../../.scratch/vendor-reuse/device.md)。此前调查记录了官方附件文件级静态观察，但本轮 `/tmp/dogzilla-pi5-src/Pi5docker code/yahboomcar_ws/src` 及原压缩包均不存在；未重新下载 121 MB 附件。下述源码细节明确是**历史静态记录，未在本轮重读或在实机确认**，可能与实机版本不同。

其一手来源是[厂商附件入口](https://github.com/YahboomTechnology/DOGZILLA/blob/3b62e37f1e25580bc1338cc9f5e2690aec4b966b/Annex_DownloadLink.txt)中的 [Pi5docker code.rar](https://drive.google.com/file/d/13sw-2CNvDGtKq7qFpDCTaIhMYWBg5tKJ/view)：121664232 字节，SHA256 `e1d56597897294dc60b3f5bf7fafd2b5f93bca9f51c88de4771d4a3220a148e9`。以下 `SRC` 表示包内 `Pi5docker code/yahboomcar_ws/src`；使用该哈希和内部路径可复核，不能当作当前安装版本。独立旧库来源为 [DOGZILLALib.zip](https://drive.google.com/file/d/1rHRu819gUmnO0LGCuovczyJ4_VC917O4/view)，历史 SHA256 `a68db7c7bba1183cf06ad8fab2c8109f04103193d6ce4aebb8b2d6267b1ff138`，版本 2.0.7。

本轮成功核对的 ROS 一手资料为[ROS 2 命令行参数设计](https://design.ros2.org/articles/ros_command_line_arguments.html)，支持名称 remap、单参数及 YAML 参数文件。它不保证厂商每个值均声明为参数，也不支持据此声称 remap 能修改消息内容或程序算法。Humble 文档页面被访问防护拦截、厂商入口网页抓取失败，未将这些失败当作来源已验证。

## 最小替代边界与仍存在的问题

| 对象及历史源位置 | 不改上游的最小做法 | 无法由该做法消除的问题 |
| --- | --- | --- |
| `SRC/bringup/launch/Navigation_bringup.launch.py:9–99` 启动多个设备节点 | 自研项目 launch 只启动必要 executable；参数文件和 remap 放自研包，保留上游原文件 | 要查实际设备、依赖、权限、启动服务；不保证未修改包在干净 Humble 环境编译成功 |
| `SRC/oradar_lidar/launch/ms200_scan.launch.py:25–66` 与 `src/oradar_scan_node.cpp:109–122,254,323–344`：有串口/型号等配置、LaserScan 发布、主机采集前时间戳 | 保留完整未修改驱动与 SDK，配置串口/坐标系；自研状态节点检测可见的断流等错误 | 话题转换不能恢复真实逐束采样时刻；若协议解码或采集时间本身错误，需更换可用未修改版本或替换相应驱动层。外部监测不能凭空获得内部错误原因 |
| `SRC/tf_publisher/tf_publisher/tf_publisher.py:16–30` 与 `yahboom_description` 的 xacro 同发 `base_footprint → base_link` 且数值不同 | 不启动重复发布节点；必要时自研最小刚体描述/静态 TF 配置，不复刻所有腿部 mesh | 仍需量测原装安装外参、明确 TF 归属；remap 话题名不等于修改 `frame_id` 字符串 |
| `SRC/yahboom_base/yahboom_base/base.py:1–61`：Twist 缩放控制，无指令超时 | 替代这一个 ROS 执行节点，调用未修改的匹配库；统一串口所有权，加入输入校验、超时停止及状态输出 | 指令单位、非线性、停止及踏步语义仍须标定；A 进程自身死亡不由自身 timer 兜底。用独立旁路同时写串口会引入竞争，不能算简单修复 |
| `SRC/yahboom_dog_joint_state/yahboom_dog_joint_state/yahboomcar_joint_state.py:39–121`：调用 `read_imu_raw`，sleep、固定 dt、零值条件复用旧值并盖新时间戳 | 与执行适配共用串口所有者；独立重写必要采集/发布逻辑，原始可用数据及缺失均记录 | 如果库内部已经把失败与合法零值混淆，外部包装不能可靠补回有效性。重新加 stamp 不能使旧样本变新；仅 remap 无法修复 |
| 旧库 `DOGZILLALib.py:121–122,155–195,477–547`；Pi5 包未含匹配库源码 | 先从实机取得匹配库/API 信息；若原库可正确使用则保持原样调用 | 旧 2.0.7 没有 `read_imu_raw`；不可拿它假定代替 Pi5 库。若所需协议能力根本不可用，重写 ROS 节点也无济于事 |

上表源码事实均回指前述官方附件和内部路径，观察的历史文本见[设备调查 §2–§6](../../.scratch/vendor-reuse/device.md)。实际库、串口和固件未知，因此没有证据支持“必然需要重写串口库”，也没有证据支持“必然只写几个 remap 就够”。

应按层决定“整段”：launch 组合 → ROS 小节点 → 串口 API/协议模块 → 固件。重写上层节点不要求重写它依赖的可用库；不修改上游也不要求重新实现 ROS 2、SDK 或整套机器人描述。用户已澄清不要求整包重写；整库/驱动重写不纳入本次主估算。自研薄节点仍承担消息类型、QoS、单位、坐标系、时间戳、串口排他和版本兼容，策略只改变维护边界，不消除这些工作。

## 人时估算：本来必做与策略新增

以下为工程判断区间，不是实测、报价或承诺。假设：人员无 ROS 实战经验但具备基本编程能力，agent 协助读码/生成/检查；机器人及操作人员及时可用，保留厂商工作环境，驱动与匹配库基本可运行；只验快速验证版典型行为。计入人的理解、审查、调试和操作时间，agent 并发不等于相同比例节省真机时间。下表各行是互斥工作包，可在 **A 内相加**；A/C/D 共同联调时间只计 A 的参与人时，汇总全队时需分别计每位参与者，不能按同一会议再次整笔重复计。

| A 的直接工作包 | 即使允许修改上游仍必做 | 采用未修改上游 + 最小替代的额外量 |
| --- | ---: | ---: |
| 核对实机环境、匹配库/API、端口与默认控制旁路 | 3–5 h | 0–1 h（记录固定版本与边界） |
| 最小启动、扫描、外参/TF 唯一来源、设备状态观测 | 4–6 h | 0–1 h（自有配置取代编辑 vendor launch） |
| 统一执行入口、串口访问安排、有效指令超时及典型停止/踏步动作 | 5–8 h | 1–3 h（用新节点替代局部补丁） |
| 可用 IMU/反馈采集、时间/单位/无效数据处理及缺失记录 | 3–5 h | 1–3 h（替代小发布节点，仍调用可用库） |
| 首包、A/C 典型运动行为联调、复查与已知问题交接 | 4–6 h | 0–2 h（替代接口差异回归） |
| **A 合计** | **19–30 h** | **2–10 h** |

因此，假设成立时该策略下 A 为 **21–40 人时**；相对可局部修改方案增加约 **2–10 人时**，不是把全部 21–40 人时算作策略代价。区间上限组合不代表概率分位；经验不足/实机等待可能进一步增加工期。A 一人两周最低投入约 20 小时，最乐观路径已几乎耗尽；应允许其他成员协助，且不能挤占 B/C/D 的必做工作。全队约 80 人时是最低投入预算参照，并非 A 的独占预算。[README §1](../../README.md)

以下为超出用户当前最小节点替代边界的风险情景，不是本轮实施计划。条件变化时须重新评估范围；不得与主估算无条件相加：

| 触发条件 | 超出上述 21–40 h 的条件性增量 | 解释 |
| --- | ---: | --- |
| ROS 雷达节点需要改，但 SDK 原样可用；自研 ROS 包装层 | 约 8–16 h | 仅替换 ROS 发布/时间/错误边界；仍需真机验证，不等于重写解包 |
| 匹配控制库无法取得或库内错误阻断必需接口，协议文档完整 | 约 16–32 h | 只替换所需串口命令/反馈子集；需协议、超时、错误帧、并发及真机回归，不默认复刻全部功能 |
| 必须重写 MS200 协议/SDK，协议完整且可测 | 约 32–64 h | 数据帧重组、校验、转圈边界、异常恢复和时序验证；这是高风险另立任务，不能当薄适配 |
| 协议/固件行为不明，必须逆向；强制断电接口不具备 | **不给有限可靠上界** | 缺资料和物理能力不是 agent 生成代码能消除；先核实或明确延期/范围决策 |

这些增量也是粗估，仅在对应缺陷实际出现时才启用；共享调查/联调步骤需要去重。允许补丁的对照方案在遇到相同缺陷时也会花时间诊断和验证，因此不能把这些总增量全说成政策净成本，净成本需拿到缺陷及补丁规模后重估。无论策略如何，重写固件/步态都不属于当前保留底层控制的范围。

## 对两周安排的含义

能支持两周快速验证的方案是把不可用小节点替换为必要的自研适配、保留已证可用的库与驱动，并尽早交出实际数据和缺失清单。若驱动/库要大改，先检查是否存在已兼容的未修改版本或可接受的非必需能力延期；切勿只为“源码干净”启动整库重写。首份采集仍要覆盖实际可获得的数据，不能为了缩小实现忽略本来可读的原始反馈。

首先需要的证据是实机库版本及 API、未修改 MS200 驱动是否运行、串口唯一所有者安排、停止/踏步是否可调用以及原始数据质量。它们决定 A 落在 21–40 h 的窄替代路径还是进入高风险分支。在取得这些证据之前，不能承诺两周约 80 人时内全队必然完成，也不能把任何条件性重写列为已批准工作。
