# B：不修改上游策略的范围、可行性与工作量

调研日期：2026-11-02。使用 `mattpocock-skills:research`，核对官方接口与 Humble 分支源码；只形成评估，不选型、不安装、不运行节点、不部署。所有人时均为工程估算，不是实测工时或完成承诺。

## 判断

**B 可以优先采用“未修改的算法包 + 自有 launch/config + 自有地图业务封装”。公开接口没有显示必须修改 SLAM 算法才能完成当前快速版。** 但还没有真机包清单、可用数据与负载结果，不能保证任一候选一定可用。

用户已明确重写边界是**最小独立节点或组件，上游库保持原样**。本文以此估算：坏的是厂商启动脚本，可以替换整个启动脚本；坏的是厂商保存业务节点，可以替换该节点并调用原版地图工具。算法从零重写仅作为超出本期的边界对照，不属于当前政策要求。

不修改上游能避免维护私有补丁和后续合并冲突，**不能避免 ROS 版本、依赖、话题、QoS、时间戳、TF、地图格式和真实数据质量的兼容问题**。完全自研会把这些问题和算法正确性一起转移给团队。

## 当前范围与证据等级

- 当前快速版为人工遥控、采集、建图、保存；建图所需运动估计仍然属于 B。B 输出已有位姿和运行状态以及保存结果。
- 加载地图后的独立定位、停靠位绑定、模式切换、导出、多地图管理进入交付版；不能把这些工作全部计入当前两周约 80 总人时。
- 以上采用[最新阶段决议 §7.14–§7.16](../architecture/interface-baseline-decisions.md#714-已确认快速验证版与交付版的功能取舍)，优先于旧调查中的两模式同时交付描述。无 ROS2 经验及 agent 协助的前提见同文件 §4；总投入见 [README §1](../../README.md#1-目标与资源)。
- [旧 B 调查](../../.scratch/vendor-reuse/mapping.md)记录了厂商附件的坏 launch、缺 Lua、保存脚本不等待结果等静态证据。本轮尝试读取其 `/tmp/dogzilla-pi5-src/` 源码，目录已不存在，因此不把旧附件结论声称为本轮重新验真的事实，更不推定真机安装也是该版本。本轮实时核对的是下面的上游接口。

## 三种替换尺度

| 尺度 | 可以做的事 | 不能解决的事 | 评估 |
| --- | --- | --- | --- |
| 配置重组、外部适配 | 自有 launch 和参数；话题 remap；时钟和 TF 分工；调用原版保存工具；把工具结果转成 B/D 业务结果 | 原始数据错误、运动估计不足、算法数值或资源问题 | 首选；通常满足不修改上游政策 |
| 替换整个外围节点 | 不运行厂商 App 保存节点，自己实现保存协调节点；不运行坏厂商 launch，自己组织可用节点 | 仍依赖算法输出和 ROS 通信；业务错误处理需自己验证 | 合理且边界清楚；很多是原本就需要的项目工作 |
| 更换现成算法包 | 厂商算法不可用时，评估原版 slam_toolbox 等 | 新算法的 odom/TF 前置、地图格式迁移、参数调优和树莓派负载不会自动解决 | 是换依赖，不是自研算法；先用同一录包做最小可行性验证 |
| 重写算法节点 | 自研运动估计、扫描匹配、闭环、图优化、栅格生成或粒子定位 | 不会消除噪声、四足俯仰起伏、标定、时序及评估难题 | 当前预算不适合；调用成熟算法库只重写 ROS 包装仍需单独注明边界，不能算算法从零自研 |

自有配置、官方公开扩展接口和外部封装均属于本次最小组件替换路线。将上游源文件复制后改名、修改其中实现，并不会在技术与维护意义上变成“未修改上游”；实现时应保留清楚的代码来源及边界。

## 粗略人时：先区分原本必做与政策增量

估算按一个 B 负责人、无 ROS2 开发经验、agent 协助阅读和实现、人负责判断与实测；包括理解、审查、运行和修正，不只统计敲代码。假设 A 尽早给出可用录包和 TF 证据、环境可启动一个成熟建图包、现场可预约，且无需自研运动估计。等待硬件的日历时间不计入人时，A/C/D 的工作也不在此表。

| 快速版 B 原本必做项 | 人时区间 |
| --- | ---: |
| 核对实际算法、scan/TF/时钟/运动估计与首份录包 | 4–6 |
| 一个候选的自有启动配置与首次建图 | 4–8 |
| 最小保存能力、产物检查、结果反馈和持久路径 | 3–6 |
| 回放及树莓派验证、基本调参、与 D 联调、记录问题 | 7–12 |
| **合计** | **18–32** |

这占约 80 总人时的 23%–40%，不是四模块平分后的保证。若 B 仅有约 20 人时，只有接近顺利路径才可能完成；未找到可用运动估计、环境不完整或真机扫描严重变形都会打破估算。

| 策略或发现 | 相对上述基线的影响，不能机械相加 |
| --- | --- |
| 保持上游不变，自有 launch/config 与薄封装 | 约新增 0–4 人时；大部分自有配置和保存封装已包含在必做项中 |
| 发现厂商 launch 或 App 保存节点不能复用 | 通常落在上述外围重做范围；若额外要求兼容旧 App 协议/数据库，另估约 4–10 人时，当前没有理由自动承接其全部旧功能 |
| 改用另一个未修改的成熟算法包 | 约新增 8–20 人时用于依赖、配置、录包对照和重新验证；仅在其输入前置成立时适用 |
| 没有可用 odom，需另集成成熟运动估计组件 | 约新增 12–30 人时起，数据质量不明时没有可靠上限；Cartographer 可选 odom 不等于实际步态下效果必然足够 |
| 自研一个可重复工作的激光运动估计节点（不属当前要求） | 数十至数百人时量级，仍不含完整 SLAM 闭环；输入与验收不足以形成可信排期 |
| 自研能用于项目验收的 SLAM 核心（不属当前要求） | 数百人时以上的研发量级；属于重新立项，不是两周任务，不能以 agent 自动生成代码抵销数据验证工作 |

交付版若继续使用成熟算法，B 的独立定位、初始化/有效性、模式配合、多地图管理、绑定持久化及重复验证，另按 **24–50 人时**作为待拆解的粗预算；多地图规则尚未确定，该数字尤其不应作为承诺。这是后续产品范围，通常不是“不改上游”造成的新增成本。

## 建议采用的判断顺序

1. 先核实真机是否已有完整可用的建图算法和配置，确认其版本、接口、输入和资源；当前不以旧附件完整性决定真机方案。
2. 保留可用的原版节点，项目维护自己的启动、参数和最小保存业务；快速版只做当前明确范围。
3. 问题若局限在启动或保存编排，就替换这个外围单元；若需要算法内部修改，先比较另一个未修改的成熟候选及其真实前置成本。
4. 若所有未修改候选在当前硬件数据上均失败，再决定缩减目标或单独立项算法研发；不要把“出现上游缺陷就从零重写整个算法”作为自动执行规则。

本轮没有机器人连接、ROS 节点启动、录包回放、地图生成、定位测试或工时测量；所以结论是接口层面可行和风险估算，不是兼容性或真机效果验收。
