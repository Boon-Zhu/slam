# 首次全量采集方案的前置调查

检查日期：2026-11-06（Asia/Shanghai）。对应 [issue #4](https://github.com/Boon-Zhu/slam/issues/4)，本轮仅准备讨论所需证据，不确定最终采集方案、不实施设备适配或正式采集。分支 `docs/device-first-capture-investigation` 从已核对远端的 `develop` / `b853b70` 创建。

## 1. 调查结论

首先需要讨论的是**控制串口与摄像头的使用方式**。现有 APP 不能提供全部反馈，另起厂商状态节点又会争抢串口；这个选择决定采集入口、遥控路径和需要补写的最小组件。单纯执行 `ros2 bag record -a` 不能采到没有发布为 ROS 话题的数据。

其余关键决策是：全量覆盖清单与缺失标记、原始数据的时间/单位记录方式、持久化与容量控制、停止录包和停止驱动的先后关系。完整标定、长期稳定性、跨机 DDS、建图算法选择不必全部完成后才讨论方案，应分别列入试采验证或后续模块工作。

前次报告建议“先处理雷达退出异常”属于执行前风险排序，不意味着讨论方案前必须修好上游驱动。可以先讨论独立 recorder、先关闭并核验 bag、再退出驱动的组织方式；它尚未实测，不能据此宣布异常已解决。

### APP 路径的一手源码补查

源文件为机器人 `/home/pi/DOGZILLA/app_dogzilla/app_dogzilla.py`：

- `return_battery_voltage()`（131–143 行）调用电池读取；TCP 建连时也读取电池（560–564 行）。所以“仅连接 TCP”也不是完全无串口交互。
- `0F` / func4（321–323 行）查询关节后调用 `motor_speed(50)`，不能视为纯只读接口。`return_ctrl_data()`、`return_posture_data()` 返回缓存设置，不是 IMU 或真实速度反馈。
- `0F` / func1、func2 切换 Standard/Fullscreen；`mode_handle()`（621 行起）只在这些模式输出 JPEG。默认及 TCP 断开后为 Home，因此 HTTP 6500 监听不保证 `/video_feed` 出帧。
- TCP 服务逐个处理连接（539–594 行），采集客户端与手机遥控需协调；不宜把这个入口当成独立多客户端数据服务。
- `/init` 调用初始化；APP 主入口还会发送 `motor_speed(50)`、`action(14)`（693–695 行）。停止再启动 APP 的恢复步骤可能触发动作，不能当作普通后台进程重启。

本轮未连接 APP TCP 或访问 `/init`，未切换模式、读取控制串口、停服务、修改厂商文件或发送运动指令。

## 4. 阻塞讨论的事项与试采门槛分开处理

| 事项 | 当前是否足以讨论 | 采集执行前仍需验证 |
| --- | --- | --- |

| 单位、轴向与时间 | 是：可以先定义原始记录及未知标记；不允许未经确认直接融合 | 静态样本、已知姿态/转动对照；保留读取前后主机时间、单调耗时、错误与样本序号；不伪称硬件采样时间 |

首次试采可承担参数测量，不必先宣称全部数据满足 B/C 融合质量。建议记录每个来源的配置、频率、QoS、有效性、时间语义和覆盖缺口；原始数据与转换后的派生数据分别保存，B/C 决定消费。该建议尚未变为共同接口。

## 5. 下一项讨论建议

**先讨论是否采用“停用 APP/OLED 的受控采集会话，由一个独立入口统一访问 UART0”这一方向。** 相比复用 APP，它能覆盖库已有的 IMU/关节/电池读取，并为之后运动接口保留单一所有者；代价是需要最小自研采集入口、摄像头接管和安全恢复流程。此处只是候选，未实现、未停服务，也未获得运动授权。

若继续保留 APP，则必须明确 IMU 获取途径及串口访问协调方式，现有 API 本身不足以给出全量方案。不能通过同时运行 `yahboom_base`、`yahboom_dog_joint_state` 和 APP/OLED 来回避这个决定。

方向确定后，再做有界静态探测，据实测决定采样频率、存储预算和会话时长；正式方案再列启动、覆盖检查、录制、停止、完整性检查、无线取回及隔离回放步骤。回放在不连接运动执行节点的环境中进行，消费者跟随播放时间。跨机 DDS 可单独验证，不作为机器人本地录包的先决条件。

同日，在上述前置调查结束后，用户报告约两分钟前出现疑似低电量趴地，并明确要求读取电池信息。以下是新增检查，不属于前文“未连接 APP TCP”的初始调查范围。

- 检查时 APP/OLED Python PID 仍为 1415/1893，6000 无已建立客户端连接。经 SSH 在机器人本机连接既有 APP TCP 6000，利用其建连自动返回电池的逻辑；三次连接均未发送应用命令，未另开 UART0，未发送运动、速度设置或复位指令。
- 三次返回均为 `$010206180021#`；字段类型/功能/长度及 APP 帧校验和通过，电池字节 `0x18`，十进制 **24**。这只验证 APP 返回帧，不构成底层反馈来源与串口互斥机制已完善的证据。

- 用户观察到趴地，软件读取到上述电量，两者分开记录。没有故障码、欠压触发阈值或事件瞬间电压，不能确认趴地原因；树莓派与 APP 当时仍可访问。
