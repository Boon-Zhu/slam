## 两条现成路径

| 项目 | 厂商 APP 服务 | 厂商 ROS base |
| --- | --- | --- |
| 电脑入口 | TCP 客户端连接机器人端口 6000；电脑键盘客户端需另行准备。现有 HTTP 路由是页面、视频及初始化，不能把它当已验证的网页遥控器 | 电脑通过 SSH 在机器人容器内发布 `cmd_vel`，或电脑 Humble 发布后通过 DDS 到机器人；前者少一层跨机 DDS 条件，键盘工具是否安装需检查 |
| 输入含义 | 按键方向码或摇杆数据，映射到厂商步幅/转向参数 | `Twist` 三轴乘 40 后交给厂商库，不应直接当成已校准 m/s、rad/s |
| 明确停止入口 | `cmd="12", num_dir=0` 调用 `stop()` | 三轴绝对值均小于 0.05 调用 `stop()`，包括全零 Twist |
| 失联与退出 | 没看到断开时 stop，也没有持续操作超时停止实现 | 没有命令超时定时器，也没有退出 finally stop |
| 同时采 IMU | APP TCP 解析器没有提供 IMU 查询转发；并开串口读者会争用 UART0 | base 本身不发布 IMU；另开厂商 JOINT 会再次打开同一 UART0 |

依据：APP 275–535（协议解析）、545–594（TCP）、612（端口）、655–671（HTTP）；BASE 6–55；SETUP 23–27 注册 `base` 入口；JOINT 39–47；LIB 122–126。

电脑通过 SSH 发布是基于 ROS topic 接口的可行操作路径推导，不是本轮端到端验证。也没有在此把新自研的“单串口所有者、同时控制和读 IMU”节点当作现成 ROS 能力。

## APP 行为细节

1. 服务创建全局 `DOGZILLA()`（APP 30）。程序启动会设 motor_speed(50) 并执行 action(14)（APP 692–695）；因此“重启服务”和“TCP 重新连接”是不同操作，前者带运动副作用。
2. TCP `accept()` 后第一次进入接收循环只主动 `return_battery_voltage()`，再阻塞 `recv()`（APP 556–566）。首次连接不自动执行站立/复位/运动。回主界面 `0F/0` 才调用 reset（APP 305–312），方向码 7 也调用 reset（380–382）。
3. 方向码 1/2 为前后，3/4 为左右，5/6 为转向，0 为 stop。默认 g_step_control=50，前后/横移比例 0.2，因此默认步幅参数为 10；转向通过 map(20..100 → 30..70) 得到 45（APP 47、53–55、352–384）。这不是实测速度。前后还设置最小步幅 5。
4. 摇杆只改 x/y（APP 338–346），归零摇杆不能等同调用完整 `stop()`；此前若有转向状态，不应假设会被该分支清零。
5. 对端正常关闭（空 recv）直接跳出；异常计数达到 10 也只跳出，然后 close、模式 Home（APP 567–594）。代码注释里的“超时计数”不是已实现的运动看门狗：listen socket 明确无 timeout（547），并且断开分支不 stop。主程序 KeyboardInterrupt 也仅 del 对象（701–704），不能据此声称退出停车。
6. TCP 使用单次 recv 后最后一组 `$...#` 解析，没有完整的流式缓冲队列（APP 566–578）。电脑客户端需考虑分包/粘包，协议发送成功不等于 MCU 执行或物理停止。

## ROS 行为细节

BASE 9 订阅 `cmd_vel`，10 新建 DOGZILLA 实例。24–26 的零速条件要求三轴同时小于 0.05；30–35 先限幅 ±100，40–42 再乘 rate=40 后发送。例：linear.x=0.1 传为厂商 x=4；angular.z=0.1 传为 4，但 LIB 192–200 又把非零小转向升至至少 ±30。因此不能把较小 Twist 当成任意缓慢可控的角速度。

LIB 176–190 对 x/y 进一步限到 ±20/±18；stop 会清 x、y、mark_time、turn（162–166）。BASE `main()` 是 spin 后 destroy/shutdown（44–55），没有显式关闭时停车和 UART 释放流程，也没有定时检测最后一次指令。停止电脑发布、关闭 SSH 或 Ctrl-C 本身不构成源码保证的停车动作。

## IMU 联采与资源所有权

APP 和 BASE 各自打开默认 UART；JOINT 39 也独立创建 DOGZILLA，64 读电机，98 读 IMU。LIB 122–126 默认 `/dev/ttyAMA0`、115200，构造会清输入缓冲；每次查询还会 flushInput（150–158），IMU 查询另有 read_all（587–598）。这些是多个进程互相干扰的直接源码机制，不是“只读 IMU 就不影响控制”。并行两个厂商进程不能据此认定可靠。宿主 OLED 等其他 UART 用户也需在真实执行前核实排除；本轮未核实现时进程。

JOINT 虽声明 0.05 秒 timer（46–47），回调中已有 0.1 秒 sleep（96），且 IMU 原始值首项为 0 时沿用旧数据（100–102）；采集频率和新鲜度不能按 timer 字面接受。发布 ROS Imu 不等于单位、时间和有效性已合格。这些问题独立于是否增加运动保护。

## 建议与下一决策

若当前只想最快验证电脑遥控动作，APP TCP 路径较少引入机器人端新控制进程，但仍要准备电脑客户端，且 APP 不能同时满足 MCU IMU 的完整采集需求。另据历史[环境核查报告](../../docs/report/pi5-image-version-audit-2026-11-02.md)第 86–97 行，已有前进与正常停止的现场观察记录；这属于历史实测证据，本轮未复测，不能说 APP 从未实测运动，也不能外推为断线停止通过。若电脑 ROS 生态、记录指令 topic 是主要诉求，原装 base 的接口更直接，不过它没有自动解决 IMU 联采，停止语义和速度映射还需明确。

对于“首次保留全部实际可获取数据，包含 MCU IMU，且电脑遥控”的组合要求，**两条原装路径都不能直接认定完整可用**。应先确定是否本次一定要控制与 IMU 同步：若是，就需要另行选择并验证单一 UART 所有者如何同时承接控制和查询（例如最小独立适配器，这是新增工作）；若接受分阶段采集，可先单独检验 IMU，再切换现成控制路径，但应明确没有运动过程 IMU，不把它称为全量同步数据。

若选择新增单所有者适配器，以 ROS 入口同时记录控制和反馈较适合完整同片段采集，但这是方案建议。串口查询本身可能等待：LIB 600–603 的 unpack 默认超时 1 秒；若读反馈与处理指令简单串行，就可能拖延后续运动/停止命令，必须设计并验证调度，不能仅合并进程便宣布解决。

上述建议没有添加 C 运动保护实现，也没有把其缺席视为已经获得项目例外。不添加 C 保护不等于省略正常停止语义。真实运动的现场条件、站立状态、人工明确停止步骤及物理停车观察仍需在执行方案中列清，不能用 TCP/ROS 发送返回替代。
