③ 节点之间传什么

人工输入 → C 输入转换 → C 运动保护 → A 运动适配 → 原有步态控制 ↑ A 雷达扫描 ────────────────┘ └────→ B 运动估计 / 建图或定位 ← A 可用反馈（待核实） A / B / C 状态 ─────→ D 运行协调 D ──调用 B 的保存/加载能力；协调停止、模式切换和就绪检查 TF：map ──[B 当前建图或定位组件]──→ odom odom ──[B 选定的唯一运动估计发布者]──→ base_link base_link ──[A 核实的外参发布者]──→ 传感器
通信形式本项目中的候选用途仍需决定
topic：连续发布扫描、反馈、原始/受保护运动输入、状态消息类型、时效、QoS；原始指令不能直接接入 A
service：快速请求/响应快速状态查询、短操作“接受”与“完成”必须区分
action：长任务、反馈/取消耗时保存/切换若需要这些语义，可考虑不要求所有操作都用 action；先看上游能力与实际耗时

命名只是候选，真实厂商话题可通过适配和 remap 接入。每段 TF 只允许一个发布者；这里没有假定已有可靠 odom。

⑥ 引导场景

点场景标签会重置状态。自由操作后若偏离步骤，重新选择场景即可。

这份原型尚不能回答什么

运动指令的分量、有效期、真实停止距离、雷达覆盖、转身空间、超时数值、定位有效性判据和地图格式，都需要后续决定或实测。原型只把“当前方向可通行”当作输入，不模拟碰撞几何。

地图与绑定只在内存中模拟；“确认停稳”由人点击代替反馈。真实系统须定义可验证的停车条件，以及 C 崩溃时 A 的兜底。按钮上的模式切换也不证明上游组件支持热切换。
