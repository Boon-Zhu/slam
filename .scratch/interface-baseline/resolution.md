## 3. 已确认：语言、构建与质量检查

### 3.1 语言选择

团队会大量使用 agent 实现代码，选择语言时优先考虑可靠性、自动检查能力和长期维护成本。

- 自研代码默认使用 **Python，并强制静态类型检查**。
- C++ 按实际接口或性能需要引入；复用上游组件保留原有语言，不为统一语言而重写。
- 自研核心逻辑需要通过类型检查，限制 `Any` 和忽略检查；第三方接口的类型缺口集中在适配层处理。
- 配置、设备数据与消息边界需要运行时校验，类型注解不能替代输入有效性检查。
- 关键状态转换与故障行为必须有测试。代码检查通过不代表真实停车或定位能力已验证。
- 已确认自研 Python 代码及类型检查目标为 Python 3.10；需要自研 C++ 时采用 C++17。开发环境与 CI 使用同一基线，机器人容器的版本证据见 §7.22，实际构建与运行仍待验证，不自动升级厂商环境。Python 检查工具已选定 Ruff、mypy、pytest；具体版本与细则由 D 的研究 issue 落实。

### 3.2 ROS2 工程组织与构建

- 使用一个统一的 ROS2 workspace 结构；各开发者拥有各自工作副本，通过 Git 协作。
- 按 ROS2 package 组织代码，使用 `colcon` 统一构建和执行已配置的包测试。
- Python 包默认使用 `ament_python`；C++、自定义接口等需要相应构建步骤的包使用 `ament_cmake`。
- 静态分析和类型检查仍需明确配置，不将 `colcon` 视为自动包含全部质量检查。

### 3.3 PR 检查与真机验证

| 验证层次 | 已确认原则 |
| --- | --- |
| PR 自动检查 | 格式、静态分析、Python 类型检查、相关包构建、无需硬件的单元与集成测试，作为合入的强制门槛 |
| 设备与运行行为验证 | 根据变更影响补充录包或真机验证记录；里程碑验收必须完成适用的真机验证 |

- 自动检查失败应修复代码，或有依据地纠正检查规则；不能让 agent 通过删除测试、扩大忽略范围绕过问题。
- 实际运动响应、停车距离与断连停车效果必须由真机验证，不能以 CI 或录包回放替代。
- **GitHub Actions 暂定采用，待通过最小试运行确认。** 尚未配置或试运行；runner、任务划分、工具版本与具体执行命令由 D 研究落实，评估与确认条件见 §7.18。
- Python 检查配置统一放在仓库根目录，由 D 负责维护与协调；各模块负责自身问题修复。
- 新增依赖由提出模块先自行检查冲突：无冲突则添加依赖并提交 PR，有冲突则提交 issue 供团队讨论，详见 §7.23。调整公共检查规则仍由受影响的负责人和 D 共同确认。
- 分支与审查规则继续遵循 [Git 提交与协作规范](../agents/git-workflow.md)，本轮未另行改变分支策略。

## 5. 已确认：复用优先，每个模块提供主要集成包

团队优先做出可用版本，尽量复用已有项目、驱动、算法和启动配置。已接受的组织方式是：

> 每个模块提供一个主要集成包，统一管理上游依赖、配置、启动入口和缺口代码；上游包保持独立，A/B/C/D 职责不变。

- “集成”指统一调用与管理，不把上游 package 嵌套到自研 package 内，也不要求搬运或改写上游源码。
- 一个集成包可以启动多个上游或自研节点；包、节点、进程与人员职责不要求一一对应。
- 能通过依赖声明、参数、remap 和 launch 完成接入时，优先使用这些方式；已有接口满足需要时，不额外编写转发层。
- 只有存在实际功能缺口时才补代码。集成包初期仅包含配置、依赖和启动文件也可以。
- 公共自定义消息包按需创建，优先复用合适的标准消息；不预先填充占位接口。
- 自研包和模块具体内部拆分仍可随实际复用方案细化。

### 7.2 已确认：C 的正常保护与 A 的执行侧兜底

- C 负责正常运动保护：判断遥控、雷达与障碍情况，限制运动并输出停止指令。
- A 必须提供指令超时停车：超过约定时间没有收到 C 的新的有效运动指令时，主动停止，不能持续执行最后一条运动指令。这项责任覆盖 C 卡住、退出或指令传输中断造成的指令缺失。
- 具体超时时长、有效指令判定、执行机制与底层停止效果，由 A/C 结合实机核实和测试确定；本轮没有指定未经验证的数值，也不代表停车能力已经实现。
- 该责任不等于已解决 A 自身进程或底层控制故障时的停车；这些情况下实际可用的停止能力仍需核实。

### 7.3 已确认：默认不运动与中断后重新授权

本节为一般规则；快速验证版的雷达故障采用 §7.9 的确认后降级操作例外。

- 项目默认采用“未收到明确指令就不行动”的原则。所有运动操作均采用“持续操作才持续运动”：没有明确、有效且未过期的持续运动授权时保持停止，松开操作即要求停止。启动完成、通信恢复或模式切换本身均不构成运动授权。
- 雷达或遥控中断、C 重启、C→A 通信中断及 A 指令超时停车后，恢复通信或组件就绪不能自动恢复运动。必须收到恢复后产生的新遥控指令，并重新经过 C 的保护检查，才可继续。
- 缓存、自动重发或重放中断前的旧指令不能作为恢复依据。新指令与有效期的具体表达和检查机制由 A/C 细化，并纳入跨模块接口约定。
- 自动停车、限制运动等保护动作不等待新的人工指令；正常传感器采集、状态监测与已授权流程内的数据处理不属于需要逐次人工授权的运动。
- 这是共同的行为约束，不指定具体算法或遥控设备，也不代表已经实现和验证。

### 7.4 已确认：避障阻挡与其他中断分别处理

下表中的雷达中断处理，在快速验证版中由 §7.9 的确认流程替代；遥控和其他通信故障仍停止运动。

| 情况 | 持续按键时 | 松开与恢复规则 |
| --- | --- | --- |
| 避障导致停止移动，且遥控、感知与执行链路仍有效 | 保留当前持续操作意图，停止被阻挡方向的移动，保持原地踏步 | 松开按键则停止踏步；保持按键且后续有效检测确认所请求运动可通行时，直接恢复移动，无需松开重按 |
| 其他原因导致中断，包括雷达或遥控中断、C 重启、C→A 通信中断、A 指令超时 | 停止运动，持续按住旧按键不能作为恢复授权 | 中断解除后，必须先松开按键再重新操作，并通过 C 的保护检查 |

- 避障阻挡是持续操作下的特殊运动状态，不等同于遥控或系统故障。“停止移动但原地踏步”与“停止踏步”必须在 A/C 接口中区分，不能默认同一条零速度指令能够表达两者。
- 持续操作期间，C 每轮依据有效感知结果重新判断所请求运动：检测到阻挡就停止相应移动，后续有效检测确认不再阻挡就允许继续。恢复依据是仍有效的持续操作与新的通行判断，不是重放缓存指令。
- “没有检测到障碍”指有效感知结果确认所请求运动空间可通行，不包括雷达无数据、数据过期或所需空间无法确认。感知中断按其他中断规则处理；具体有效性与通行判定方法由 C 细化。
- 原地踏步的底层接口、实际位移和机身扫过范围需由 A/C 核实与验证，并据此设置保护距离；当前记录的是期望行为，不能据此认定厂商底层已支持或在所有障碍距离下均可安全执行。具体参数与实现留到模块方案及真机验证，不继续在本轮展开。
- 避障期间若同时发生其他中断，按其他中断规则停止运动并要求松开后重新操作，不能以避障状态继续踏步。

### 7.8 已确认：四级故障响应与版本划分

当前工作版本为快速验证版，以跑通流程、获取数据为目标，不要求完成全部边界条件验证；下一个交付版本要求完整验证约定场景与故障响应。此前第一版的保护要求作为目标保留，但不能将快速验证版的运行结果当作交付验收通过。

| 层级 | 用户定义的情况 | 目标响应 |
| --- | --- | --- |
| 0 | 系统完全正常 | 按持续操作与避障规则运行，不自动产生运动授权 |
| 1 | 不影响运动的传感模块断流或明显故障 | 原地踏步 |
| 2 | 通信模块故障，例如与操控者断联 | 停止行为 |
| 3 | 运动模块故障，或 A 自身失效 | 直接强制断电 |

- 本表记录目标响应。各故障具体归级、检测来源、恢复条件及并发故障的处理尚需细化；不默认所有传感器故障都属于层级 1。“不影响运动”是否包括对运动保护的影响，需结合雷达等具体数据源明确。
- 层级 1 的原地踏步仍受持续操作约束；0→1 的确认流程与雷达降级例外见 §7.9。避障阻挡与设备故障是不同情况，不能直接套用同一恢复规则。
- 层级 3 的实际断电接口、触发路径及运动模块失效时是否仍可执行，由 A 核实。普通停止命令不等于强制断电；不能将目标行为写成已实现能力，也不默认为此改动原装硬件。
- 用户允许将当前实现或验收过于复杂的层级处理延期到交付版本。具体延期项目根据接口核实与实现复杂度确定；快速验证版应明确记录实际实现和验证范围，不要求穷尽边界条件，也不宣称未验证行为已通过。
- A 集中报告其可检测的设备与数据错误、D 记录并报告全局状态的责任保留。运动指令链路的失联检测责任及 A 自身失效的处理见 §7.26；具体检测与执行能力仍需核实。

### 7.9 快速验证版补充：0→1 的确认与雷达降级

- 从层级 0 转为层级 1 时，必须提供可由用户确认的故障反馈；用户确认前不接受新的运动操作，但松开按键仍可停止踏步。确认本身不产生运动指令，不重放故障前指令。
- 用户未采纳“雷达故障一律采用层级 2 停止响应”的建议，要求快速验证版在雷达不可用时进入确认反馈流程，并优先保持原地踏步。
- 故障前正在前进不能证明故障后所请求运动空间仍可通行，即使障碍静止，机器人继续移动也会改变间距。用户确认表示接受感知降级，不代表雷达恢复或避障能力已验证。
- 已确认的雷达故障流程：立即停止平移和转向，在原有持续操作下保持原地踏步并等待确认；等待期间松开按键则停止踏步。
- 用户确认后，可以重新按住方向键执行平移或转向，不限于原地踏步。仍采用“持续操作才持续运动”，由操作者观察环境；系统明确提示“雷达不可用，避障未生效”。这项确认不解除通信故障或运动模块故障对应的限制。
- 这是快速验证版对 §7.3–§7.4 雷达中断处理的特定调整；其他通信故障仍按层级 2 处理。交付版是否保留该降级模式及相应验收范围尚未决定，不能将其视为满足原有雷达中断停车要求。

### 7.26 已确认：运动指令链路失联与 A 自身失效

| 失联位置 | 检测与响应责任 |
| --- | --- |
| 用户操作端 → D | D 检测操作连接失效，通知 C 停止；不能持续转发旧操作来维持运动 |
| D → C | C 检测有效操作指令超时，经 A 停止运动 |
| C → A | A 检测运动指令超时，自行执行停止，不等待 C 发来停止命令 |

- 上述通信失联按层级 2 停止行为，包括停止踏步；恢复后需松开再重新操作。D 能接收到故障信息时负责汇总与反馈。
- A 自身失效按层级 3 处理，目标响应为强制断电。快速验证版不增设额外冗余。
- 强制断电仍是待核实的执行能力，不能假定已经失效的 A 仍能执行断电。沿用 §7.8，由 A 核实原装系统的断电接口及失效时可用性，D 协同确认集成触发路径；此项纳入模块研究 issue，不在本轮展开实现。
- 若原装系统无法支持该故障下的断电，必须记录能力缺口，按既定版本取舍流程处理；不能以普通停止替代强制断电并宣称已实现，也不能将“不增设冗余”解释为已保证自动断电。
- 具体检测方式和超时数值留给模块研究。A 报告设备与数据错误、B/C 根据报告响应的约定保留；错误报告链路失联不自动等同于已经确认 A 自身失效。

- 本例外仅指 A 向 D 报告错误的通道故障，而 A 自身、设备、运动指令链路以及其他必要通信均正常。快速验证版按正常运行策略继续，不因该上报通道单独故障触发运动降级或停车，也不新增独立检测或冗余机制。
- “按正常运行策略”描述运动处置，不代表上报通道健康。未收到错误报告不能用作系统完全正常的证据；已观察到的通道异常仍须记录和反馈。
- 本例外不扩大到 A→B/C 的必要通信、运动指令失联或 A 自身失效；这些情况继续按已确认的故障规则处理，不能因 D 未收到报告而免除响应。
- A/B/C/D 各自维护一份模块日志，试运行结束后交叉核对，用于定位事件发生、处理及上报之间的差异。各模块负责自身日志，D 沿用集成职责协调核对；具体格式、字段与收集方式由相关模块细化。
- 日志交叉核对属于事后分析，不替代运行中的超时停止或强制断电能力。交付版上报链路的检测与响应在后续故障验证设计中完善。
